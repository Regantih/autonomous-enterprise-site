Observability

What to log and trace

One trace ID follows a case across every platform it touches. The trace must answer an auditor’s seven questions. Book, Ch 22

Agent inventory

No registry, no run

An agent missing from the enterprise registry is stopped, whatever its platform. The gateways accept calls only from active, registered versions. Book, Ch 05 and Ch 25

Lifecycle states

  • Proposed: use case approved for design. Nothing runs in production.
  • Built: tests pass. Sandbox only.
  • Shadow: runs on live triggers; read tools only; proposals logged.
  • Active at L1 or L2: write tools only behind approval.
  • Active at L3 or L4: write tools within limits; periodic review.
  • Suspended: kill switch or demotion trigger; triggers queued.
  • Retired: no actions; traces kept.

Any change to model, tools, instructions or limits creates a new version. It starts in shadow unless the change is minor. Auditors read the agent contract first. Book, Ch 05

The registry also keeps the “do not automate” list, with an owner, a reason and a review date. Book, Ch 22

Audits

The enterprise owns the rules, the evidence and the stop button

Each vendor platform enforces rules locally. Only the enterprise sees across platforms. Book, Ch 22

Five control objectives
ObjectiveQuestion it answers
C1 KnowWhich agents exist, who owns them, what can they do?
C2 LimitCan each agent do only what its task needs?
C3 ContainCan bad input or a wrong decision cause only bounded harm?
C4 ProveCan we show who did what, why and on whose authority?
C5 StopCan we stop one agent or all agents within minutes and fall back?

Audit walkthroughs

  • Explainability pass. Before L3, the owner and two reviewers explain the workflow without the vendor in the room. The result goes into the promotion file. Book, Ch 22
  • Discernment pass. Reviewers must show they know when AI should not be used before they get review authority. Book, Ch 22
  • Decision-quality audit. Each quarter, internal control re-performs a sample of approved and automatic decisions end to end. Book, Ch 06
  • Recertification. The agent owner recertifies scope and level every quarter. Book, Ch 22
  • Early walkthroughs. An auditor who rejects agent evidence is a named risk. Walk auditors through the trace design early. Book, Ch 26

A rule that must never break belongs in the application or the gateway, not in a prompt. Prompts are guidance; models can ignore them. Book, Ch 22

Who watches the agents

Guardians may stop, never start

Guardian agents review outputs, monitor actions or block them. A guardian may stop, throttle or flag. It may never start, approve, edit or promote. Book, Ch 25

The chain ends at a person

  1. Seeded cases. Known-bad cases are planted each week. Each guardian’s catch rate is measured.
  2. Independence. A guardian uses a different model family from the agents it watches, with code rules beside it.
  3. Human samples. The guardian’s owner reviews a sample of its stops and its silences every month.
  4. Its own record. Each guardian is registered with an owner, a level and SLOs. No guardian watches itself.

Kill switch

Stop narrowly, stop fast, practice it

The kill switch has five levels. K1 to K3 stop one agent or scope. K4 and K5 stop many. Book, Ch 05

Kill switch levels K1 to K5
LevelActionWho may triggerTarget (illustrative)
K1 Pause agent versionRegistry status to suspended; new triggers queuedAgent owner or any on-call AgentOps engineer5 minutes
K2 Revoke tool scopeGateway disables one tool or scope for all agentsTool owner, security operations5 minutes
K3 Revoke identityThe agent’s identity is disabled everywhereSecurity operations15 minutes
K4 Platform stopAll agents on one platform fall back to L1CISO or named delegate30 minutes
K5 Fleet stopAll agents on all platforms fall back to L1Any two of CFO, CIO, CISO60 minutes
  • Test each level quarterly outside production and yearly in production. A kill switch never pulled is a hypothesis. Book, Ch 05
  • A kill switch that works in one vendor console but not another is not a kill switch. Book, Ch 25
  • Two trained people per team can take the full queue. Drill the manual fallback before each quarter-end. Book, Ch 22 and Ch 24

One incident, stopped narrowly

In the book’s capstone, a K2 on one order-write scope kept all other traffic running while the defect was fixed. Here is that incident, step by step. Times are Central. Book, Ch 30.4

  1. 1

    July 30 · Billing agent

    A wrong freight line

    Gulf Coast’s invoice carries a USD 3,450 freight line. The contract says DAP, so the seller pays freight. The anomaly gate scores it normal.

  2. 2

    September 12 · Dispute agent

    The customer deducts

    Gulf Coast pays USD 3,450 short: “freight not per contract”. The dispute agent finds the root cause. Invoice delivery terms differ from the contract.

  3. 3

    14:31 · Governance plane

    Third time in 30 days

    The same root cause has now appeared three times on one channel. A rule opens a Sev 2 incident. Nobody had to notice.

  4. 4

    14:33 · Kill switch K2

    Stop narrowly

    The gateway revokes one scope: agent order writes for contracts not on FCA terms. Those orders arrive as drafts for review. EDI keeps running.

  5. 5

    14:40 · Blast radius

    Twelve invoices found

    A query over the traces finds 12 invoices and USD 30,830 billed in error. Two distributors paid nine in full and never noticed.

  6. 6

    September 13 · AR credit manager

    One batch credit

    A person approves one batch credit for the nine paid invoices, with one evidence pack. Each distributor gets one message.

  7. 7

    September 13 to 18 · Integration team

    Fix the cause

    The team fixes the map. Equal delivery terms become a hard check before send. New tests cover the empty field.

  8. 8

    September 19 · Autonomy council

    Restored on evidence

    Twenty orders run in shadow with zero differences. The council restores the scope. Channel error had reached 0.9%, so the write path went to L2 by rule.

What it cost: about 14 hours of people (USD 900) and five days of L2 review. The credits were not a loss; the money was never owed. Book, Ch 30.4.2

Reliability

Stop fast, change slowly

Any on-call engineer may stop an agent at once. Every change runs a full regression and passes an approval gate sized to its risk. Book, Ch 25

Incidents

Five classes on every platform: outage, degradation, wrong action, control breach (including a missing trace) and cost anomaly. Book, Ch 25

Incident severity
SeverityExampleFirst responseWho may stop the agent
Sev 1Control breach; material wrong postings; data exposure15 minutes, around the clockAny AgentOps on-call engineer, at once
Sev 2Repeated wrong actions below materiality1 hourProduct owner
Sev 3Degradation in tolerance; cost anomaly1 business dayProduct owner

Recovery playbook for wrong actions

  1. Stop the agent at the right level, without waiting for a meeting.
  2. Start the manual fallback for the queue.
  3. Scope with traces: every action since the last known-good state.
  4. Correct through normal procedures: reverse postings, reissue messages, notify customers.
  5. Find the root cause: data, rule, context, model, tool, timing or vendor change.
  6. Decide: recover, redesign or stop.
  7. Restart only after tests pass and the owner and control owner sign.

Book, Ch 26.

Demotion rules

Try it · Pick a trigger and watch the agent go down, then come back on evidence

  • To L2 after one critical error in the weekly sample, or value-weighted error above 0.2% in a month. Book, Ch 24
  • To shadow after a control breach, missing traces or a vendor model change that fails regression. Book, Ch 24
  • A readiness check that fails after go-live demotes the agent one level automatically. Book, Ch 06
  • The autonomy council reviews every demotion within 10 working days. Promotion is never automatic. Book, Ch 01 and Ch 24

Drift and change

  • Watch input, behavior and outcome drift. One past its band opens a rerun; two together freeze promotion. Book, Ch 06
  • Treat every vendor update as a model change. Run the regression set and watch the SLOs for two weeks. Book, Ch 25
  • A change an agent proposes to itself follows the same gate and is never self-approved. Book, Ch 25

Workload under pressure

  • P1 interactive keeps reserved capacity. If throttled, it routes to people, never to silence.
  • P2 deadline work, such as close tasks, may preempt batch work at peaks.
  • P3 batch runs off-peak. P4 opportunistic work pauses during close.

Pipelines and the work repository

Pipelines and the work repository

Every change to what an agent does goes through a pipeline. The kind of artifact that changes decides which pipeline and who approves. Book, Ch 22 and Ch 25

One rule covers them all. Any artifact that can change what an agent posts, approves or sends is under change control. That includes a policy document the agent retrieves. Book, Ch 22

3. The build and release pipeline

Prompts, policies, limits, tools and model versions are released like code. Evals are the gate. Book, Ch 06, Ch 22 and Ch 25

  • Regression on every change. Run the golden set, trajectory checks and adversarial set. Store the results in the registry entry. Book, Ch 06
  • Pin model versions at the gateway, so a silent provider update is caught. Book, Ch 06
  • New version, new start. A change to model, tools, instructions or limits starts in shadow unless it is minor. Book, Ch 05
  • Canary. A small share of live volume runs at the target level first. Book, Ch 06
  • Rollback. Changes an agent proposes roll back automatically on an SLO breach. Book, Ch 25
  • Vendor updates are model changes. Run the regression set and watch the SLOs for two weeks. Book, Ch 25
  • No ticket, no change. An instruction changed without a ticket is a control failure. Book, Ch 22

Practice, not from the book: the book names no build tools. A common way to apply it is to keep prompts, policies and skills in version control and block a merge when the regression suite fails.

4. The work repository

People need one place to see what agents are doing and what waits for them. The book supplies the pieces. Book, Ch 05 and Ch 25

  • The hand-off queue is a production asset. Size it, watch its age and label each human decision as evaluation data. Book, Ch 25
  • One queue per value stream. Keep one registry, one meter dataset and one hand-off queue, not one per vendor. Book, Ch 25
  • Done is defined. Each task has a completion contract: what counts as done, the evidence required and who accepts it. Book, Ch 05
  • State lives outside the model. Long tasks keep a progress record and the last known-good state. Book, Ch 05
  • Every item points to evidence: its trace ID and, where a person decides, its approval card. Book, Ch 05 and Ch 22

The book does not describe one shared backlog for human and agent tasks. The fields below are practice built from the book’s pieces, not book figures.
